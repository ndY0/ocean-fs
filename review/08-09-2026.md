this is what i caught reading through the codebase. they only target the production code :

- not using context to precisely drop a resource when possible, immediately resorting to drop : not idiomatic rust
- empty implementations, for exemple Drop on WalSyncGroup
- hardcoded magic values : values that are not user config, should at least be configurable at build time. timeouts are a good exemple
- hardcoded values that should be computed : for instance, shardcount is suppose to be derived  from core count, but set to 4. carefull, becausee this most often has transient impacts, for exemple changing this must be reflected on cache pool sizes. this require a lot of attention and impact diagnostic.
- GC config is partially harcoded
- scrub config is entirely defaulted, anti entropy partially, heal config entirely defaulted.
- object_cache, metadata_cache, negative_cache, prefetch_config entirely or partially defaulted
- misslabeled MetricRegistrar -> MetricRegistrer
- hardcoded loop timers, should be build config too
- there are monotonic increments based on u64, for exemple on get/put, in what time would they exhaust ?
- L1 cache eviction is linear scan. this is bad, since caching invalidation is very load dependent, the comment assumption is false. we must refactor using a tree based approach. same goes for L2
- OperationTimeouts not wired properly. not extended with recent operations values. never overloaded by build conf.
- anti-antropy rebuild merkle trees each time from scratch. wouldnt it be more efficient to build it as we go ? what would be the performance hit ?
- we reconstruct the peer merkle tree, but it could send it to us already build, assuming a mutual binary protocol => protocol exists, not wired
- we could select a reandom subset of metadata for the merkle tree exchange, to relieve resource pressure, and run it more frequently
- anti entropy doesnt use erasure coding optimisations all the time. sometimes it push to heal pool, some other times it  use local Cauchy matrices.
- i dont like the way metrics pollute the constructors. they should be a trait implementation allowing to initialize them, and update/ lookup, much cleaner.
- garbage collection is very coarse : it run on all the deleteion key space at once. could it be possible to optimize running on a subset, more frequently ? subject of discussion
- same question for the orphan reaper. in fact, every durability subprocess could get a strategy fa;ily config  that would dictate their behaviour, since they essentially all run on the same lookup a column family + act principle
- heal worker usae dynamic dispatch, this is not acceptable, especially for the ec decoder, wich will prevent inlining. also use to_vec, heap allocate, not ok
- grps merkle sservice could use the cached merkle trees from above
- Hinted handoff : magic constants, should be build config
- hintedhandoffs are in memory. what happens if the node crash ? also, send handoff one by one, very wastfull, should group per node as possible
- as a matter of principlle, any remote fetch between nodes regardless of protocol should be batched beest effort
- scrub worker raise the same questions as anti-entropy. does not use Cauchy directly although
- are grpc call sites all using the pooled channels connections ?
- as i am reading the fetch server side, i realize that it has a strong opinion on the order of how to reconstruct the blob : local then ec then remote. this is reasonnable, but does not cover all possible configuration a client might want. maybe they want best possible tail latency, at the cost of network. i think the actual ordering should be the subject of a strategy
- fetch does not cluster fetched by member allocation. it should bundle them to reduce network calls.
- every reference of Encoder / Decoder seems to be dynamic. doesnt that prevent inline ?
- i see lots of opportunities in the code for buffer pools. for instance, SegmentGrpcService preallocate a vector to write a segment into it. but why dont we preallocate a bunch of vector at startup, then rotate them ? this pattern must be toroughly inspected
- seal worker and delete endpoints are in the write directory, thats weird.
- we have a strong copupling to rocksdb, without an  enum trait approach. this raise the cost of changing clumnar data store greatly
- wal writer does not use  any io optimisation. we should discuss this matter, since it is on the hot path
